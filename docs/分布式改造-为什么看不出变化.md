# 为什么"看不出变化"才是对的

> 这份文档回答三个问题：
> 1. 这次改造到底改了什么（界面为什么一点没变）
> 2. 按你定的六段项目模板，这件事该怎么讲
> 3. 面试官追问时怎么答，以及别把话说过头的地方

---

## 0. 一句话回答

**因为这次改的不是功能，是"功能出错时的行为"。**

界面是功能的外投影：能上传、能排计划、能看视频，这些东西一行没动，所以页面一个像素都不会变。
真正变的东西只在三种时刻才看得见：

| 时刻 | 改造前 | 改造后 |
|---|---|---|
| 服务中途重启 | 任务消失，进度条永远停在 62% | 任务还在库里，worker 起来接着跑 |
| 两个人同时交任务 | 后到的被信号量挡住，且看不到"还有几个" | 队列里排着，页面显示"前面还有 2 个任务" |
| worker 跑到一半被 kill | 没救，用户只能重传 | 租约到期，任务被另一个 worker 捡走 |

所以判断标准从来不是"看界面有没有变"，而是**"杀掉一个进程，看任务会不会丢"**。
前者测功能，后者测约束。这次改的是约束。

一个更直白的类比：给车换刹车盘、换刹车油，车还是那辆车，外观一模一样。
只有踩急刹、或者下长坡的时候才知道换了。

## 1. 定位：这次改的是哪一层

用你自己那套"八层框架"的话说，这次动的是 **⑦评测 / ⑧可观测** 以及底下的**状态层**，不是 ①~⑥ 的任何业务逻辑。

- ①编排 ②上下文 ③工具 ④状态 ⑤检索 ⑥输出 —— 只有 ④ 被换掉
- ⑦评测：新增 15 个队列用例（全项目 59 例）
- ⑧可观测：新增 `obs.py` 结构化日志 + `/api/metrics`

**这解释了"看不出变化"的全部原因**：④ 是状态层，它不产生任何用户可见的输出，它只决定"出事的时候数据还在不在"。

一句更准确的话（面试也这么说）：

> 这不是"把单体拆成微服务"，是**把进程内状态外置，让 API 变成无状态、worker 变成可水平扩展的**。
> 单机多进程，不是多机分布式。叫它"分布式"会被追问，叫它"状态外置"经得住追问。

## 2. 改造前后对照（带真实数字）

### 2.1 四张表看改动

| 维度 | 改造前 | 改造后 | 改完解决什么 |
|---|---|---|---|
| 任务状态 | `TASKS: dict`（app.py 内存） | `tasks` 表 | 第二个进程看得见；重启不丢 |
| 任务执行 | `asyncio.create_task()` | `jobs` 表 + 租约 | 崩了能回收；能开任意多个 worker |
| 结果存储 | `data/sessions/*.json` | `sessions` 表 | 并发写不再有"读到半个文件" |
| 限流 | `_SLOTS = asyncio.Semaphore(2)` | 队列并发 + `ahead_of()` 位次 | 多实例下才算得对 |
| 日志 | `print` / 异常栈 | `data/logs/*.jsonl` 一行一 JSON | 能 grep、能算耗时 |
| 指标 | 没有 | `/api/metrics`（仅本机） | 队列积压/worker 存活能看出来 |

新增 5 个文件、共 700 多行：`store.py`(276) `queue.py`(216) `worker.py`(145) `pipeline.py`(105) `obs.py`(103)。
`app.py` 反而从 500 多行减到 350 行——因为流水线搬走了。

### 2.2 本机真实跑出来的数

改造后实测 5 个任务（`/api/metrics` 原始输出）：

```json
"stats": { "tasks": {"done": 5}, "jobs": {"done": 5}, "avg_task_seconds": 11.2 }
"workers": [
  {"id": "洛-79520-433f", "pid": 79520, "jobs_done": 2},
  {"id": "洛-79520-ce8b", "pid": 79520, "jobs_done": 2}
]
"legal_queue": true
```

两个 worker 同 pid、不同 id、各干完 2 个——这就是"内嵌 2 并发"在跑。
单条任务各阶段耗时（日志里抄的，单位 ms）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| parse 解析文档 | 9.4 | CPU 密集，几十毫秒级 |
| knowledge 抽知识点 | 3006.6 | **等模型**，秒级 |
| schedule 排期 | 7.9 | 纯算法 |
| guidance 生成说明 | 5177.4 | **等模型**，秒级 |

**这组数字是这次改造里最值得记住的一条论据**：
整个请求 11 秒里，数据库只占个位数毫秒，99.9% 的时间在等模型 API。
所以"SQLite 撑不撑得住"这个问题，答案是"它根本不是瓶颈，瓶颈在模型调用"。
面试里能主动说出这句话，比背"WAL 支持高并发"有用十倍。

### 2.3 唯一的核心 SQL

```sql
-- 一整段在 BEGIN IMMEDIATE 事务里
SELECT id, task_id, payload, attempts, max_attempts FROM jobs
 WHERE (status='pending' AND lease_until <= :now)
    OR (status='running' AND lease_until <  :now)   -- 租约过期 = 上一个 worker 死了
 ORDER BY id LIMIT 1;

UPDATE jobs SET status='running', worker=:wid,
                lease_until=:now + 900, attempts=attempts+1
 WHERE id=:id;
```

三个要点，每个都能被追问：

1. **`BEGIN IMMEDIATE` 立刻拿写锁**，读和写之间不许别人插队。否则两个 worker 可能读到同一行。
2. **`lease_until` 是租约不是锁**：锁要靠人释放，进程崩了就永远不释放；租约到期自动失效，不需要任何"解锁"代码。
3. **语义是 at-least-once，不是 exactly-once**：worker 崩在"模型已调用、结果还没写回"之间，任务会被重跑，模型会重复计费。所以 `max_attempts=2`——宁可标失败让用户重提交，也不无限重试烧钱。

## 3. 你可以亲眼验证的三处变化

### 3.1 界面上唯一的两处（真的只有这两处）

- 排队时：`排队中（前面还有 2 个任务）` —— 这个数字来自 `queue.ahead_of()`，按 job id 算，不是进程内计数器
- 重试时：`重试中（1/2）` —— 第一次失败不报错，用户看到的是"还在跑"，因为下一次可能就成

除此之外前端一行没改。**这就是"看不出变化"的全部真相。**

### 3.2 三个可复现实验（建议自己跑一遍，比看文档记得牢）

**实验 A：任务会不会丢**

```bash
# 终端 1
python -m uvicorn app:app --port 8000

# 页面交一个任务，等进度到 30%（抽知识点那一步最慢，有 3 秒窗口）
# 立刻 Ctrl+C 杀掉

# 终端 2：看库里
python -c "import sqlite3;c=sqlite3.connect('data/app.db');print(c.execute('select id,status,attempts,lease_until from jobs').fetchall())"
```

你会看到 `status='running'`、`lease_until` 是个未来时间戳（现在 + 900 秒）。
**重启服务，什么都不用做**，worker 起来后：要么等租约到期（15 分钟）被回收，要么手动把 `lease_until` 改成 0 立刻回收，任务自己跑完。
改造前这一步是：任务凭空消失，`sessions/` 里什么都没有，用户只能重传。

**实验 B：能不能开第二个 worker**

```bash
# 终端 1：只跑 API，不跑任务
WORKER_INLINE=0 python -m uvicorn app:app --port 8000
# 终端 2、3：两个独立 worker 进程
python -m core.worker --concurrency 1
python -m core.worker --concurrency 1
```

一次交 3 个任务，第 3 个显示"前面还有 2 个"，前两个被两个进程分别抢走。
`/api/metrics` 里能看到 3 个不同 worker（不同 pid）。改造前：第二个终端根本没意义，任务压根不在库里。

**实验 C：worker 被 kill -9**

跑任务时直接 `kill -9 <worker pid>`。任务停在 `running`，租约到期后被另一个 worker 捡走，`attempts` 变成 2。
如果第二次还崩，`status='failed'`，`last_error` 里留最后一次异常——不会无限重试。

### 3.3 一个只有本机能看的接口

```bash
curl http://127.0.0.1:8000/api/metrics
```

返回四块：`stats`（任务/队列计数、平均耗时、最近 5 条错误）、`queue_depth`、`workers`（30 秒内有心跳的）、`legal_queue`。

`legal_queue = false` 的含义很具体：**队列里有活，但 30 秒内没有任何 worker 心跳**。
这正好是"关了内嵌 worker 却忘了起独立 worker"那个事故的特征。指标不是拿来画图的，是拿来指认具体故障的。

## 4. 按六段模板讲这件事

模板是你定的：**需求分析 → 能力拆解 → 工具选型 → 学科映射 → 实施步骤 → 面试话术**。
下面每一段我都写"填什么"+"为什么这么填"，因为这段才是真正要学的东西。

### 第一段 · 需求分析（说触发条件，不说技术名词）

❌ 错：我要把项目改造成分布式架构。
✅ 对：三个真实触发条件——

1. 分享给同学后，有人传 300MB 扫描教材，解析十几分钟，把别人的任务全堵住
2. 我自己改代码重启服务，正在跑的任务直接消失，用户看到永远停在 62% 的进度条
3. 我想"多开一个进程一起跑"，发现根本做不到——任务绑死在 API 进程里

**为什么这么填**：需求分析里出现技术名词（分布式、微服务、消息队列），面试官第一反应是"你在套模板"。
出现的是现象（堵住、消失、做不到），他才会想"那你怎么解决"。

### 第二段 · 能力拆解（三件事，不要拆成十件）

| 能力 | 一句话 | 落到哪个文件 |
|---|---|---|
| 状态外置 | 进程不再持有任何业务状态，杀掉不留痕迹 | `core/store.py` |
| 抢占式调度 | 多个 worker 抢同一个队列，只有一个能拿到，崩了自动回收 | `core/queue.py` |
| 可观测 | 出事时能一句话指认是"没 worker"还是"任务报错" | `core/obs.py` + `/api/metrics` |

**为什么只拆三件**：能力拆解的用途是"排期"。拆成十件排不完，拆成三件每件都有明确的验收动作。
验收就是第 3 节那三个实验——能复现才算做完。

### 第三段 · 工具选型（讲否决理由，不讲优点）

选型的价值全在"为什么不选另一个"。

| 候选 | 结论 | 真实理由 |
|---|---|---|
| Redis 做锁/队列 | 不用 | 本机没有 Redis，写了也验证不了；而租约这个原语 SQLite 行锁就能表达。接口只有 `claim()` 一个方法，真要换只改这一处 |
| PostgreSQL | 不用 | 2C2G 上多跑一个 PG 进程不值。所有 SQL 收在 `store.py` 一个文件，换 PG 改这一处就行——**这句话是承诺，不是借口，因为确实一眼能看完** |
| Celery / RQ | 不用 | 它们自带 broker（Redis/RabbitMQ），等于为了一个队列引入第三个进程；而我要的只是"抢一行、改一行" |
| SQLite WAL | 用 | 多进程并发读写；`BEGIN IMMEDIATE` 给到行级争抢的效果；零额外进程 |

**为什么这么填**：面试官听到"我用了 Redis 做分布式锁"，下一句必然是"为什么不用 MySQL 行锁"。
你答不上来，前面讲的全塌。反过来你先说"我考虑过 Redis，但它给的原语和 SQLite 行锁是同一个，而我需要的是能验证的东西"——这句就是分水岭。

### 第四段 · 学科映射（"原来这就是××"）

这一段是你模板里最有辨识度的部分，作用是**把课程名换成能力名**。

| 课上的词 | 这个项目里的具体形态 |
|---|---|
| 临界区 / 互斥 | `BEGIN IMMEDIATE` 里那 8 行 SELECT+UPDATE |
| 死锁预防 | 用 IMMEDIATE 一次拿写锁，避免"读锁升级写锁"时的互相等待 |
| 事务隔离 | WAL 模式下写不阻塞读；`busy_timeout=15s` 是退让而不是失败 |
| 看门狗 | `lease_until` + 每 1/3 租约续一次，超时即判死 |
| 心跳 / 保活 | `workers.last_seen`，30 秒无心跳算掉线 |
| 幂等 / 至少一次语义 | `save_session` 用 upsert；任务重跑不产生两条结果 |
| 有界重试 vs 无限重试 | `attempts < max_attempts`，参数错误重试一万次也没用 |
| 原子追加写 | `os.write` + `O_APPEND`（< PIPE_BUF 的追加写在 POSIX 下是原子的） |

**为什么这么填**：这一段是给面试官看的"我知道我在用哪门课的东西"。
没有这一段，你的项目就只是"抄了个教程"；有了这一段，它是"课程知识的落地"。

### 第五段 · 实施步骤（每步带锚点）

模板要求每步标**第几步 / 框架哪层 / 哪个文件**，照做：

| # | 做什么 | 框架层 | 文件 | 验收 |
|---|---|---|---|---|
| 1 | 建表：tasks / sessions / jobs / workers / meta | ④状态 | `store.py` | `sqlite3 data/app.db ".tables"` 五张表 |
| 2 | 老 `sessions/*.json` 一次性导入，打标记防重复 | ④状态 | `store.py::_import_legacy_sessions` | meta 表有 `legacy_imported` |
| 3 | `TASKS` dict 全部换成 `store.update_task` | ④状态 | `app.py` | 重启后 `/api/task/{id}` 还能查到 |
| 4 | 流水线搬出 app.py（否则 worker 要 import FastAPI，成环） | ①编排 | `pipeline.py` | `python -c "from core import pipeline"` 不报错 |
| 5 | 入队 + 抢任务 + 续租 + 收尾 | ④状态 | `queue.py` | 两进程抢 10 个任务，不重不漏 |
| 6 | worker 独立进程 + 内嵌模式共存 | ①编排 | `worker.py` | `WORKER_INLINE=0` 时行为不变 |
| 7 | 评测：15 个用例，双进程抢任务用真子进程 | ⑦评测 | `tests/test_queue.py` | 59 例全绿，连跑三轮 |
| 8 | 结构化日志 + metrics 从状态表派生 | ⑧可观测 | `obs.py` + `/api/metrics` | `legal_queue` 能正确变 false |

**顺序为什么是这样**：1→3 先把状态搬走（此时行为完全不变，可以随时回滚），4→6 才动执行路径，7→8 最后补。
如果先写 worker 再搬状态，中间会有一段时间"两套状态同时在用"，那是最难调的时候。

### 第六段 · 面试话术（90 秒版，能背下来）

> 我这个项目一开始是单进程的：任务表是内存 dict，任务用 `asyncio.create_task` 直接跑，结果写 JSON 文件。
> 分享给同学之后暴露了三个问题：有人传大文件把别人的任务堵住；我重启服务，跑到一半的任务直接消失；想多开一个进程分担，发现根本做不到。
>
> 我做的事是把状态外置：任务、结果、队列全搬进 SQLite（WAL）。执行改成"抢任务"——一个 worker 用 `BEGIN IMMEDIATE` 里的一条 UPDATE 占住一行，同时写一个 15 分钟后的 `lease_until`。
> 这个租约是关键：它不是锁，不需要谁去释放。worker 崩了，租约到期这行自动回到可抢状态，被别的 worker 捡走。代价是语义只能做到"至少一次"，不是"恰好一次"——崩在模型已调用、结果还没写回之间，任务会重跑、模型会重复计费，所以我把重试上限设成 2，宁可标失败让用户重提交。
>
> 结果：现在 API 进程随时能杀，重启任务还在；worker 可以开任意多个，排队位次按库里的 job id 算，不是进程内计数器。
> 实测一次分析 11 秒，其中数据库个位数毫秒，3 秒在抽知识点、5 秒在生成说明——瓶颈从来不在库，在模型调用。
>
> 这套东西我只写了 700 行，因为它没有引入任何新进程：租约这个原语 SQLite 行锁就能给，Redis 能给的也是同一个东西。

**为什么这么讲**：
- 开头是问题不是技术（"堵住/消失/做不到"）
- 中间主动交代代价（at-least-once、重复计费）——**主动说局限的人显得可信**
- 结尾给数字（11 秒 / 3 秒 / 5 秒），数字是"真跑过"的唯一证据
- 最后一句挡住"为什么不用 Redis"

## 5. 面试官会追问的 8 个问题

| 追问 | 答的核心（一句话就够，多了反而露怯） |
|---|---|
| 为什么不用 Redis？ | 原语相同，环境没有；`claim()` 是一个方法，切点留着 |
| 两个 worker 会不会抢到同一个任务？ | 不会。SELECT+UPDATE 在 IMMEDIATE 事务里，写锁互斥 |
| 为什么不直接 `UPDATE ... WHERE id=(SELECT ...)` 一条语句？ | 可以，但要把"取哪一行"和"改哪一行"绑定，同事务更直观也更安全 |
| at-least-once 重复执行怎么办？ | 结果用 upsert，重跑覆盖不产生两条；模型费用重复，所以限制 2 次 |
| 租约 15 分钟怎么定的？ | 最长阶段（解析大 PDF）的经验值 ×3，且每 5 分钟续租一次，跑多久续多久 |
| SQLite 能撑多少并发？ | 写是全局串行的，但一次写是毫秒级；实测 11 秒里库占个位数毫秒，瓶颈在模型 |
| 怎么证明多进程真的能跑？ | 测试用真子进程抢任务。同进程读同一个 SQLite 永远成功，证明不了任何事 |
| 这套能上多机吗？ | 不能直接上。SQLite 走网络文件系统不安全，多机要换 PG 或加 Redis——这是我知道的下一个切点 |

**最后一条必须自己说出来。** 面试里最掉分的不是"做不到"，是"以为做到了"。

## 6. 语言无关：这套东西在 Java / C++ 里长什么样

你说市面上 Java 和 C++ 岗多——这套能力恰恰是**换语言不掉价**的那一类，因为原语是同一组：

| 这里的做法 | Java 后端 | C++ / 嵌入式 |
|---|---|---|
| `BEGIN IMMEDIATE` + 条件 UPDATE | MySQL 行锁 / `SELECT ... FOR UPDATE` | `flock()` 文件锁 / 共享内存原子 CAS |
| `lease_until` 到期自动回收 | Redisson `tryLock(leaseTime)` 的看门狗 | 看门狗定时器，喂狗超时复位 |
| `workers.last_seen` 心跳 | 注册中心 / Eureka 心跳 | 心跳包 / CAN 保活帧 |
| `attempts < max_attempts` | RabbitMQ 手动 ack + 死信队列 | 状态机里的重试计数 + 降级 |
| at-least-once | 几乎所有 MQ 的默认语义 | 报文重传 + 幂等键 |

所以这段经历有两种讲法，取决于投哪个岗：

- 投 **Java 后端**：直接讲"我用 SQL 行锁 + 租约实现了分布式锁和任务队列，没引 Redis"，术语全对得上
- 投 **嵌入式 / 底层**：换成"状态外置 + 看门狗 + 心跳 + 有界重试"，这就是 BSP 里那套可靠性设计，同一个东西

**唯一不能做的是把名词换成"分布式系统"就完事**——那会招来一堆你答不上的追问。

## 7. 这次改造的真实局限（别吹过头）

按重要性排：

1. **它是单机多进程，不是多机。** 这条原来是个坑：`worker.py` 的注释写过"把 worker 放到别的机器共享 data/app.db"，而 SQLite 的 WAL 依赖本地文件锁和 `-shm` 共享内存，放 NFS/SMB 上会静默损坏数据。写这份文档时已经把注释改成明确的边界说明——**注释比代码更容易撒谎，因为它不被测试覆盖**。
2. **写是全局串行的。** WAL 只解决了"读不阻塞写"，写还是一个接一个。几十个任务无所谓，几百个并发就要换 PG。
3. **没有优先级和超时。** 一个卡死的任务会占着租约 15 分钟，期间别人只能等。
4. **`/api/rerun` 还是同步的。** 它是单用户的一次主动操作，十几秒返回比"排队 + 轮询"体验好；但严格说这是唯一还留在请求线程里的长任务。
5. **没有真正的"恰好一次"。** 要做得加幂等键（把 task_id + 阶段名做唯一约束），这是下一步而不是已完成项。

**这五条不是缺点清单，是"我知道边界在哪"的证明。** 面试里能说出第 1 条的人，比说"我做了个分布式系统"的人可信得多。
